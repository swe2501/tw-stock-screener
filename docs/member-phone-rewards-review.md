# 手機迎新與任務上限：待共同套用

狀態：只在 `shared/justy/member-lifecycle` 準備，沒有修改共用 DB、Auth 設定或啟用 SMS。網站單獨更新不會發券或改變真實點數上限。

## 核定規則

- 每個帳號一次「市場觀察員・5 天功能體驗券」，必須以 Auth 真正 `phone_confirmed_at` 驗證。填入電話或修改 metadata 不算。
- 每支電話只屬於一個帳號；電話以國碼正規化後產生加鹽指紋，不向會員端暴露其他使用者或電話。解除綁定、換號、刪除帳號不開放舊號碼給別帳號重新領取。真正號碼移轉／救援須另由客服核實，不提供客戶端重置入口。不要修改或輪替活動 salt。
- 新會員是註冊時間不早於正式活動起日；既有帳號不溯及新迎新券。活動起日尚未設定。
- 發出待啟用券；一個日曆月內啟用，啟用後 120 小時。範圍僅 fhedge／breadth，不是完整會員級別、儲存容量或篩選額度升級。
- 網站進站先查資格，簡訊未開通時不廣告可領券；完成驗證後以同一 RPC 自動申領。網路失敗下次進站可重試，帳號／電話唯一鍵和交易鎖防重複；入帳前不在本機發點或製造虛假券。
- 一般任務每日 60、每週合計 300；台北日界線、週一零時。新手八項一次合計 500 例外。所有一般類別含原先另計的學習、連續任務共用總額。
- 一般未來任務面額大於 40 的收至 40，週筆記 30；停發新的連續打卡附贈券。已發券、已入帳點數、帳本與歷史領取紀錄保留。活動／任務原有 active 開關保留。
- 單筆及一鍵領取都用同一限制，重送回原領取結果。點數可用餘額與兌換價格仍由原帳號服務決定。

## 套用順序與檢查

1. 與合夥人比對共用 DB 的 migration 版本與現行 Auth，先在測試 DB 套用既有依賴；不可將舊腳本重新覆蓋新版函式。
2. 在 `member-voucher-levels.sql` 後套 `member-phone-welcome.sql`。此為一次性 migration：含 Auth trigger，若現有正規化電話重複會整筆停止，需先人工處理，不能任選一人覆蓋。
3. 所有現行任務、學習核驗、任務工作紀錄和 `member-task-bulk-claim.sql` 之後，最後套 `member-rewards-policy-v4.sql`。新版狀態需回傳 `rewards_policy_version=4`，確認前網站保留舊後端數字。後續不可重跑舊腳本覆蓋新版 wrapper。
4. 用測試會員實際綁定、收簡訊、驗證、進站提醒、重試、領取、啟用與到期驗收。不可只以本機 mock 宣稱線上 SMS 可用。
5. 確認簡訊服務／費用及公告後，再明確設定活動起日並同時啟用 policy 與 `phone-welcome-observation-v1` 定義。兩者預設關閉；本文不是活動啟用 SQL。

未完成：首次與一般任務同一完成事件的跨任務證據去重，仍須以工作紀錄 ID 做後續關聯。這次沒有宣稱完成該項，也沒有變更舊推薦活動或八個兌換商品。

## 已執行隔離驗證

- PostgreSQL/PGlite：真實驗證欄位、電話格式正規化、同號不同帳號拒絕、解除／換號／刪帳防重領、活動關閉、他人資料隔離、手動啟用完整 120 小時。
- PostgreSQL/PGlite：一般類別每日及每週合計、首次 500 例外、滿額原單重試、一鍵領取、私有 wrapper 權限、週一界線、歷史帳本保留。
- 網站 Playwright：淺深色、手機桌機、資格查詢不誤觸強制綁定、略過提醒、驗證後伺服器發券、帳號切換清理、未開服務不顯示獎勵承諾。
